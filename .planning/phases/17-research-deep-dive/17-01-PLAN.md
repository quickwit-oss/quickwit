## Document Structure

### 1. Overview
- Problem statement: Metrics pipeline currently has no durability guarantees
- Solution: Integrate with existing ingest_v2 durability infrastructure
- Scope: WAL, checkpointing, gossip, retry, rate limiting (Phases 18-22)

### 2. Architecture Decision Records (ADRs)

For each open question from 17-RESEARCH.md, document the decision:

**ADR-1: WAL Directory Separation**
- Decision: Use separate `metrics_wal_dir_path` configuration
- Rationale: Isolation prevents cross-contamination, independent recovery
- Consequences: New config field needed

**ADR-2: Queue ID Namespace**
- Decision: Prefix with `metrics/` - `metrics/{index_uid}/{source_id}/{shard_id}`
- Rationale: Prevents collision with logs queues, clear ownership
- Consequences: Queue iteration must filter by prefix

**ADR-3: MRecord Format**
- Decision: Reuse existing MRecord enum without metrics-specific variants
- Rationale: Doc and Commit variants sufficient, same recovery logic
- Consequences: Metrics bytes encoded same as log bytes

**ADR-4: Position Tracking Model**
- Decision: Per-shard positions identical to logs model
- Rationale: Proven pattern, reuses ShardPositionsService
- Consequences: Time-range metadata tracked separately in split metadata

**ADR-5: Initial Replication Factor**
- Decision: Start with replication_factor=1 (no replication)
- Rationale: Simpler MVP, add replication as separate enhancement
- Consequences: Single-node durability only for v0.3

### 3. Integration Specifications

**3.1 WAL Integration (Phase 18)**
- Module location: `quickwit-ingest/src/metrics/`
- Key types to create: `MetricsWal`, `MetricsWalConfig`
- Integration with: `MultiRecordLogAsync` (shared instance)
- Queue management: Create on first metric, delete on empty after truncate

**3.2 Position Tracking (Phase 19)**
- Reuse: `Position` enum from quickwit-proto
- New type: `MetricsShardPosition` (wrapper with metrics-specific metadata)
- Persistence: Checkpoint to metastore (existing `Checkpoint` type)
- Events: `LocalShardPositionsUpdate` with metrics source_uid

**3.3 Cluster Gossip (Phase 20)**
- Reuse: `ShardPositionsService` as-is
- Chitchat key format: `indexer.shard_positions:{index_uid}:{source_id}:{shard_id}`
- Note: Same key format works because source_id distinguishes metrics sources

**3.4 Retry & Error Handling (Phase 21)**
- Reuse: `RetryParams` configuration
- Error classification: Same transient/permanent logic
- Recovery: Read WAL on startup, replay uncommitted records

**3.5 Rate Limiting (Phase 22)**
- Reuse: `RateLimiter` and `RateMeter` types
- Config: `rate_limit_bytes_per_sec`, `burst_limit_bytes`
- Capacity tracking: `check_enough_capacity()` before append
