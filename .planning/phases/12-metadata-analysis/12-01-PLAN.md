## Metrics Query Pruning Requirements

### Query Patterns
Document typical metrics query patterns:
1. Time range (always present) - "metrics from last hour", "between T1 and T2"
2. Metric name - "cpu.usage", "memory.used"
3. Tag filtering - service=web, env=prod, host=server-001

### Pruning Dimensions

| Dimension | Query Frequency | Cardinality | Pruning Level |
|-----------|-----------------|-------------|---------------|
| time_range | 100% | N/A | Postgres (indexed) |
| metric_name | 100% | 100-1000 per split | Postgres (TEXT[]) |
| tag_service | 80% | Low (<100) | Postgres (TEXT[]) |
| tag_env | 50% | Very low (<10) | Postgres (TEXT[]) |
| tag_datacenter | 50% | Very low (<20) | Postgres (TEXT[]) |
| tag_region | 40% | Low (<50) | Postgres (TEXT[]) |
| tag_host | 40% | High (1000+) | Parquet bloom filter |
| attributes | 20% | Variable | Parquet bloom filter |

### Cardinality Threshold Decision
Document the 1000 threshold for Postgres vs Parquet:
- Below 1000: Store in Postgres TEXT[] with GIN index
- 1000+: Use Parquet bloom filters (configured in Phase 11)
- Rationale: Postgres arrays efficient up to ~1k, beyond that bloom filters more practical

## Two-Tier Pruning Strategy

### Tier 1: Postgres Metastore (Coarse Filtering)
Document what goes in the new metrics_splits table:
- time_range_start, time_range_end (BIGINT, indexed)
- metric_names (TEXT[], GIN index)
- tag_service, tag_env, tag_datacenter, tag_region, tag_host (TEXT[], GIN index)
- num_rows, size_bytes (BIGINT, for query planning)
- split_metadata_json (TEXT, full MetricsSplitMetadata)

Expected pruning: Eliminate 90%+ of splits before touching storage.

### Tier 2: Parquet (Fine-Grained Filtering)
Document what stays in Parquet:
- Bloom filters on high-cardinality columns (tag_service, tag_env, tag_datacenter, tag_region, tag_host, attributes)
- Row group statistics for timestamp predicates
- Configured in Phase 11: FPP=0.01, NDV estimates

Expected pruning: Further reduce I/O within selected splits.

### Why Separate Table (metrics_splits)
Document decision rationale:
1. Different pruning needs than logs (metric names vs full-text search)
2. Independent schema evolution (no backward compatibility risk)
3. Optimized indexes for metrics query patterns
4. Clean separation of concerns
