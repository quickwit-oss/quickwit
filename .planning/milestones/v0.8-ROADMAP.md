# Milestone v0.8: Parquet Compaction

**Status:** Not started
**Phases:** [31](#phase-31-metadata-foundation)-[36](#phase-36-integration-testing--verification)
**Total Plans:** 18

## Overview

Node-local time-windowed sorted compaction for Parquet metrics splits. Eliminates unbounded split accumulation ([GAP-001](../../docs/internals/adr/gaps/001-no-parquet-compaction.md)), improves compression through sorted storage (25-33% expected from Husky data), and establishes the merge pipeline architecture that generalizes to logs/traces in future phases. Build order follows strict data dependencies: [metadata foundation](#phase-31-metadata-foundation) (every downstream component reads window_start, sort_schema), then [ingestion window enforcement](#phase-32-ingestion-window-enforcement) (compaction needs pre-sorted window-scoped inputs), [merge policy](#phase-33-merge-policy) (pure algorithm), [merge executor](#phase-34-merge-executor) (highest complexity, validated in isolation), [actor pipeline](#phase-35-actor-pipeline--monitoring) (wiring), [integration testing](#phase-36-integration-testing--verification) (end-to-end verification). The 5 new compaction actors mirror the existing Tantivy [MergePipeline](../../quickwit/quickwit-indexing/src/actors/merge_pipeline.rs) supervision model exactly.

Closes gaps: [GAP-001](../../docs/internals/adr/gaps/001-no-parquet-compaction.md) (no Parquet compaction), [GAP-003](../../docs/internals/adr/gaps/003-no-time-window-partitioning.md) (no time-window partitioning), [GAP-004](../../docs/internals/adr/gaps/004-incomplete-split-metadata.md) (incomplete split metadata).

## Phase Details

### Phase 31: Metadata Foundation
**Goal**: All metadata types, database schema, and core functions exist so downstream phases can read and write compaction-aware split metadata
**Depends on**: [Phase 30](v0.7-ROADMAP.md) (v0.7 Metrics Query)
**Requirements**: [META-01](../REQUIREMENTS.md#metadata--schema), [META-02](../REQUIREMENTS.md#metadata--schema), [META-03](../REQUIREMENTS.md#metadata--schema), [META-04](../REQUIREMENTS.md#metadata--schema), [META-05](../REQUIREMENTS.md#metadata--schema), [META-06](../REQUIREMENTS.md#metadata--schema), [META-07](../REQUIREMENTS.md#metadata--schema), [META-08](../REQUIREMENTS.md#metadata--schema), [PIPE-10](../REQUIREMENTS.md#merge-pipeline)
**Success Criteria** (what must be TRUE):
  1. Husky's `event_store_sortschema.proto` (synced from dd-source) provides SortSchema, SortColumn, SortColumnDirection, and RowKeys types; a Husky-style string (e.g., `metric_name|host|env|timeseries_id|timestamp/V2`) parses into the prost-generated Rust types with multi-column support, direction suffixes, and timeseries_id hash tiebreaker
  2. [MetricsSplitMetadata](../../quickwit/quickwit-parquet-engine/src/split/metadata.rs) contains window_start, window_duration_secs, sort_schema (SortSchema proto), num_merge_ops, RowKeys (sort-key min/max boundaries), and per-column zonemap regex -- and round-trips through PostgreSQL and Parquet key_value_metadata without data loss
  3. The list_metrics_splits_for_compaction RPC returns only splits matching a given (index_id, window_start, sort_schema) scope
  4. publish_metrics_splits atomically stages new splits and marks replaced splits in a single PostgreSQL transaction
  5. The canonical window_start(timestamp, duration) function produces correct results for negative timestamps, zero-crossing boundaries, and all edge cases, verified by proptest

Plans:
- [ ] 31-01: Sync event_store_sortschema.proto from dd-source (SortSchema, RowKeys types) and implement string parsing
- [ ] 31-02: MetricsSplitMetadata extensions and PostgreSQL migration
- [ ] 31-03: Metastore RPCs (list_for_compaction, atomic publish with replace)
- [ ] 31-04: Canonical window_start function with proptest

### Phase 32: Ingestion Window Enforcement
**Goal**: Every new metrics split is pre-sorted within a single time window, so the compaction pipeline receives clean inputs
**Depends on**: [Phase 31](#phase-31-metadata-foundation)
**Requirements**: [INGEST-01](../REQUIREMENTS.md#ingestion), [INGEST-02](../REQUIREMENTS.md#ingestion), [INGEST-03](../REQUIREMENTS.md#ingestion), [INGEST-04](../REQUIREMENTS.md#ingestion), [INGEST-05](../REQUIREMENTS.md#ingestion), [OPS-06](../REQUIREMENTS.md#monitoring--testing)
**Success Criteria** (what must be TRUE):
  1. [ParquetIndexer](../../quickwit/quickwit-indexing/src/actors/parquet_indexer.rs) partitions incoming rows into separate accumulators per time window (15-min default), and each produced split contains data from exactly one window
  2. Each split's rows are sorted by the configured sort_schema within the window, verified by reading back and checking sort order
  3. Data arriving beyond the configurable late data acceptance window (4-hour default, per-index) is rejected with rejection counted in metrics; data between warning threshold (1-hour) and hard cutoff emits warning metrics but is accepted
  4. Splits written after compaction_start_time contain window_start metadata; splits written before are ignored by compaction
  5. All new Parquet splits have column index and offset index enabled, verified by reading Parquet metadata

Plans:
- [ ] 32-01: Window-partitioned accumulator in [ParquetIndexer](../../quickwit/quickwit-indexing/src/actors/parquet_indexer.rs)
- [ ] 32-02: Sort-at-write and late data handling
- [ ] 32-03: Property-based tests for window boundaries, sort stability, and tiebreaker

### Phase 33: Merge Policy
**Goal**: A pure-logic merge policy determines which splits within a window should be merged, preventing both unbounded split accumulation and excessive re-compaction churn
**Depends on**: [Phase 31](#phase-31-metadata-foundation)
**Requirements**: [POLICY-01](../REQUIREMENTS.md#merge-policy), [POLICY-02](../REQUIREMENTS.md#merge-policy), [POLICY-03](../REQUIREMENTS.md#merge-policy)
**Success Criteria** (what must be TRUE):
  1. WindowedSortMergePolicy groups splits by size into levels and selects merge candidates that reduce split count toward target size (256 MiB default)
  2. Policy parameters (target size, max fanin, maturity age) are configurable per index and the defaults produce reasonable merge plans for typical metrics workloads
  3. Splits below the minimum merge threshold are not selected for re-compaction, preventing late-data churn

Plans:
- [ ] 33-01: WindowedSortMergePolicy with proptest coverage (reference: [StableLogMergePolicy](../../quickwit/quickwit-indexing/src/merge_policy/stable_log_merge_policy.rs), Husky planner.go)

### Phase 34: Merge Executor
**Goal**: A standalone merge executor performs k-way sorted merge of Parquet splits with correct metadata computation, schema evolution, and memory isolation
**Depends on**: [Phase 31](#phase-31-metadata-foundation), [Phase 32](#phase-32-ingestion-window-enforcement) (needs real pre-sorted splits to test against)
**Requirements**: [PIPE-03](../REQUIREMENTS.md#merge-pipeline), [PIPE-04](../REQUIREMENTS.md#merge-pipeline), [PIPE-05](../REQUIREMENTS.md#merge-pipeline), [PIPE-06](../REQUIREMENTS.md#merge-pipeline), [OPS-05](../REQUIREMENTS.md#monitoring--testing)
**Success Criteria** (what must be TRUE):
  1. ParquetMergeExecutor merges N pre-sorted Parquet files into a single sorted output file, preserving global sort order across all input rows
  2. Merged output [MetricsSplitMetadata](../../quickwit/quickwit-parquet-engine/src/split/metadata.rs) contains the union of all input metric names, tags, time ranges, and correct RowKeys (min/max sort-key boundaries) and zonemap regex recomputed from merged data
  3. When input splits have different column sets, the executor produces a union schema with null fill for missing columns -- and fails explicitly on type conflicts
  4. Compaction runs in a separate DataFusion memory pool; if memory is exhausted, the merge fails gracefully without killing the process
  5. Unit tests cover merge policy level selection, merge executor sort correctness, sort schema parsing, and metadata computation

Plans:
- [ ] 34-01: ParquetMergeExecutor with StreamingMergeBuilder (reference: [MergeExecutor](../../quickwit/quickwit-indexing/src/actors/merge_executor.rs), Husky merge_order.go)
- [ ] 34-02: Schema evolution and merged metadata computation (RowKeys + zonemap regex)
- [ ] 34-03: Memory pool isolation and unit test suite

### Phase 35: Actor Pipeline & Monitoring
**Goal**: The full compaction pipeline runs autonomously -- planning, downloading, executing, uploading, publishing merges with supervision, GC, and production monitoring
**Depends on**: [Phase 33](#phase-33-merge-policy), [Phase 34](#phase-34-merge-executor)
**Requirements**: [PIPE-01](../REQUIREMENTS.md#merge-pipeline), [PIPE-02](../REQUIREMENTS.md#merge-pipeline), [PIPE-07](../REQUIREMENTS.md#merge-pipeline), [PIPE-08](../REQUIREMENTS.md#merge-pipeline), [PIPE-09](../REQUIREMENTS.md#merge-pipeline), [OPS-02](../REQUIREMENTS.md#monitoring--testing), [OPS-03](../REQUIREMENTS.md#monitoring--testing), [OPS-04](../REQUIREMENTS.md#monitoring--testing)
**Success Criteria** (what must be TRUE):
  1. ParquetMergePlanner queries the metastore, selects merge candidates via the policy, and schedules merges without duplicate scheduling (inventory tracking)
  2. The full pipeline (plan -> download -> execute -> upload -> publish) completes a merge cycle and the planner receives feedback that triggers the next cycle
  3. ParquetMergePipeline supervisor detects actor failures and restarts the pipeline with mailbox recycling, matching Tantivy [MergePipeline](../../quickwit/quickwit-indexing/src/actors/merge_pipeline.rs) behavior
  4. Prometheus metrics expose compaction runs started/completed/failed, merge duration, split count per window, write amplification ratio, and compression ratio
  5. Janitor GC handles MarkedForDeletion metrics splits with a grace period before S3 deletion, preventing read-write conflicts during queries

Plans:
- [ ] 35-01: ParquetMergePlanner (reference: [MergePlanner](../../quickwit/quickwit-indexing/src/actors/merge_planner.rs)) and ParquetMergeSplitDownloader (reference: [MergeSplitDownloader](../../quickwit/quickwit-indexing/src/actors/merge_split_downloader.rs))
- [ ] 35-02: ParquetMergePublisher with atomic publish and planner feedback (reference: [Publisher](../../quickwit/quickwit-indexing/src/actors/publisher.rs))
- [ ] 35-03: ParquetMergePipeline supervisor (reference: [MergePipeline](../../quickwit/quickwit-indexing/src/actors/merge_pipeline.rs)) and [IndexingService](../../quickwit/quickwit-indexing/src/actors/indexing_service.rs) integration
- [ ] 35-04: Monitoring metrics and janitor GC extension

### Phase 36: Integration Testing & Verification
**Goal**: End-to-end correctness is verified through the production HTTP/gRPC stack, and the compaction state machine is exhaustively verified against [TLA+ invariants](../../docs/internals/specs/tla/TimeWindowedCompaction.tla)
**Depends on**: [Phase 35](#phase-35-actor-pipeline--monitoring)
**Requirements**: [OPS-01](../REQUIREMENTS.md#monitoring--testing), [OPS-07](../REQUIREMENTS.md#monitoring--testing), [OPS-08](../REQUIREMENTS.md#monitoring--testing), [OPS-09](../REQUIREMENTS.md#monitoring--testing)
**Success Criteria** (what must be TRUE):
  1. An E2E test ingests metrics via HTTP, triggers compaction, and queries the compacted data through the REST API -- verifying that query results are identical before and after compaction
  2. Stateright exhaustive model checking verifies the compaction state machine (ingest -> compact -> publish -> GC lifecycle) has no reachable invariant violations
  3. All 10 [TLA+ invariants](../../docs/internals/specs/tla/TimeWindowedCompaction.tla) (TW-1/2/3, CS-1/2/3, MC-1/2/3/4) are enforced via debug_assert! in implementation code and verified by tests
  4. A DST crash-recovery test simulates upload-succeeded-but-publish-not-committed and verifies no data loss or duplication on recovery

Plans:
- [ ] 36-01: E2E compaction correctness test through HTTP/gRPC
- [ ] 36-02: Stateright model checking and [TLA+ invariant](../../docs/internals/specs/tla/TimeWindowedCompaction.tla) verification
- [ ] 36-03: DST crash-recovery test
