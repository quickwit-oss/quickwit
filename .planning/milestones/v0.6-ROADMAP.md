# Milestone v0.6: DataFusion SQL API

**Status:** 🚧 IN PROGRESS
**Phases:** 27-29
**Total Plans:** ~8

## Overview

Add a direct DataFusion SQL endpoint to the metrics engine with **external orchestration**. This means:

1. **Root endpoint** returns split assignments (not results)
2. **Leaf endpoint** executes SQL on provided splits
3. **External orchestrator** (ClickHouse, custom client) handles parallelization

This architecture enables:
- ClickHouse to directly query Quickwit metrics via Arrow Flight
- Custom orchestrators to control query execution
- Efficient distributed execution without Quickwit managing it

## Architecture

**External Orchestration Model:**

```
┌──────────────────────────────────────────────────────────────────┐
│                    EXTERNAL ORCHESTRATOR                          │
│            (ClickHouse, pandas, custom client)                    │
│                                                                  │
│  1. Call Quickwit root: "plan_metrics_splits"                   │
│     Input: SearchRequest (index, time range, filters)            │
│     Output: List of (Split, Nodes) assignments                   │
│                                                                  │
│  2. For each node, call leaf: "execute SQL on splits"            │
│     Input: SQL + assigned splits                                  │
│     Output: Arrow IPC data                                        │
│                                                                  │
│  3. Aggregate results locally                                     │
└──────────────────────────────────────────────────────────────────┘
        │                              │
        ▼                              ▼
┌─────────────────────┐    ┌─────────────────────┐
│   QUICKWIT ROOT     │    │   QUICKWIT LEAF     │
│                     │    │                     │
│  plan_metrics_splits│    │  MetricsSqlLeaf     │
│  • Consult metastore│    │  • Receive SQL      │
│  • Prune by time    │    │  • Receive splits   │
│  • Return splits +  │    │  • Execute DataFusion│
│    node assignments │    │  • Return Arrow IPC │
│                     │    │                     │
│  NO SQL execution   │    │  NO metastore access│
└─────────────────────┘    └─────────────────────┘
```

### Phase 28: Root Split Planning Endpoint

**Goal:** Create root endpoint that returns split assignments for external orchestration
**Depends on:** Phase 27
**Plans:** 3

Plans:
- [ ] 28-01: Split planning protobuf messages and SearchService method
- [ ] 28-02: gRPC adapter for PlanMetricsSplits
- [ ] 28-03: REST endpoint POST /api/v1/metrics/plan-splits

**Details:**

The `plan_metrics_splits` endpoint:
1. Takes a `SearchRequest` (reuses existing pruning logic)
2. Consults metastore for matching splits
3. Applies time range and filter pruning
4. Returns splits with node assignments

```protobuf
message PlanMetricsSplitsRequest {
  SearchRequest search_request = 1;  // Reuse existing!
}

message PlanMetricsSplitsResponse {
  repeated SplitAssignment split_assignments = 1;
  uint32 num_splits = 2;
  uint64 elapsed_micros = 3;
}

message SplitAssignment {
  SplitIdAndFooterOffsets split = 1;
  string index_uri = 2;
  repeated string node_ids = 3;  // Nodes that can serve this split
}
```

REST endpoint:
```
POST /api/v1/metrics/plan-splits
{
  "index_id_patterns": ["otel-metrics-*"],
  "start_timestamp": 1705000000,
  "end_timestamp": 1705100000
}

Response:
{
  "split_assignments": [
    {"split_id": "...", "index_uri": "s3://...", "node_ids": ["node-1", "node-2"]},
    ...
  ],
  "num_splits": 42,
  "elapsed_micros": 1234
}
```

### Phase 29: Arrow Flight Leaf Service

**Goal:** Add Arrow Flight protocol to leaf nodes for streaming SQL results
**Depends on:** Phase 28
**Plans:** 2

Plans:
- [ ] 29-01: FlightService implementation wrapping MetricsSqlLeafService
- [ ] 29-02: Integration tests with Arrow Flight client

**Details:**

Arrow Flight on **leaf nodes** (not root):
- `GetFlightInfo`: Validate SQL + splits, return schema
- `DoGet`: Execute SQL on splits, stream Arrow batches

FlightDescriptor contains SQL + splits:
```json
{
  "sql": "SELECT metric_name, avg(value) FROM metrics GROUP BY metric_name",
  "splits": [{"split_id": "...", ...}],
  "index_uri": "s3://bucket/index"
}
```

ClickHouse integration:
```sql
-- ClickHouse calls each Quickwit leaf node via Flight
SELECT * FROM arrow_flight(
    'grpc://quickwit-node-1:9100',
    '{"sql": "SELECT ...", "splits": [...], "index_uri": "..."}'
)
```

## Key Decisions

| Decision | Rationale | Status |
|----------|-----------|--------|
| External orchestration | Quickwit provides endpoints, external client parallelizes | ✓ Decided |
| Root returns splits, not results | Enables external control of execution | ✓ Decided |
| Reuse SearchRequest for pruning | Leverage existing time range/filter logic | ✓ Decided |
| Leaf receives splits in request | No metastore access at leaf | ✓ Decided |
| Arrow Flight on leaf | ClickHouse calls leaves directly | ✓ Decided |
| SQL passed to leaf, not root | Root doesn't parse SQL — just plans splits | ✓ Decided |

## Example: ClickHouse Integration

```sql
-- 1. ClickHouse (or orchestrator) calls Quickwit root for split planning
-- This happens via HTTP or could be a ClickHouse table function

-- 2. For each returned split assignment, ClickHouse calls the leaf
SELECT * FROM arrow_flight(
    'grpc://node-1:9100',  -- From split assignment
    '{"sql": "SELECT ...", "splits": [{"split_id": "abc"}], "index_uri": "s3://..."}'
)
UNION ALL
SELECT * FROM arrow_flight(
    'grpc://node-2:9100',
    '{"sql": "SELECT ...", "splits": [{"split_id": "def"}], "index_uri": "s3://..."}'
)
-- ClickHouse handles the UNION and aggregation
```

## Success Metrics

1. **Functional:** External client can plan splits + execute SQL on leaves
2. **Performance:** Split planning < 100ms, leaf execution scales with data
3. **Compatibility:** Arrow Flight works with ClickHouse, pyarrow, polars
4. **Simplicity:** Quickwit endpoints are simple; orchestration is external

## Out of Scope for v0.6

- Internal orchestration (Quickwit coordinating leaves)
- SQL parsing at root level
- Result aggregation at root level
- Multi-index joins
- Prepared statements
