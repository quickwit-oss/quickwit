# Merge OSS

Follow these steps to merge the latest changes from the upstream open-source repository into this fork.

## Step 1: Check that we are on the main branch

Run: `git branch --show-current`

If the current branch is not `main`, abort and ask the user to switch to the main branch first.

## Step 2: Ensure main is up to date

Run: `git pull origin main`

This ensures we're working from the latest code.

## Step 3: Create a merge branch

Get the git username: `git config user.name | tr ' ' '-' | tr '[:upper:]' '[:lower:]'`

Get today's date: `date +%Y-%m-%d`

Create and checkout a new branch: `git checkout -b {username}/merge-oss-{date}`

## Step 4: Fetch the latest from oss remote

Run: `git fetch oss`

This fetches the latest commits from the upstream OSS repository (`ssh://git@github.com/quickwit-oss/quickwit.git`).

## Step 5: Attempt the merge

Run: `git merge oss/main --no-edit`

If the merge completes without conflicts, skip to Step 7.

## Step 6: Resolve conflicts

If there are merge conflicts:

1. Run `git diff --name-only --diff-filter=U` to list all conflicted files.
2. **Start a resolution log** — keep an in-memory list of `(path, strategy, one-line rationale)` tuples as you go. Strategy is one of: `take-ours`, `take-theirs`, `merge-both`, `regen` (file is regenerated by tooling). You will use this log to write the PR body in Step 10, so the entries must be specific enough that a reviewer can reconstruct what happened (e.g. "kept our `setup_dogstatsd_exporter` function" beats "kept ours").
3. For each conflicted file:
   - Read the file and examine the conflict markers (`<<<<<<<`, `=======`, `>>>>>>>`).
   - Analyze both sides of the conflict (ours = private fork, theirs = OSS upstream).
   - Attempt an automatic resolution:
     - If the conflict is in generated files (e.g., `Cargo.lock`), prefer regeneration later.
     - If the conflict is in code, try to reconcile both changes logically.
     - If the conflict is in `Cargo.toml` dependencies, merge both sets of changes.
   - **Auto-resolve without asking** for the following cases:
     - **`.github/CODEOWNERS`**: Always take ours. Upstream's `@quickwit-oss/*` team references don't exist in the DataDog org, so merging them in is noise. The DataDog fork manages its own ownership.
     - **GitHub Actions version bumps**: If OSS updated action versions (e.g., checkout, setup-python, setup-node), take the OSS version. Keep any fork-specific steps (ADMS override, DD STS token, etc.) intact.
     - **Tantivy rev updates**: Always take the OSS tantivy rev.
     - **scorecard.yml (modify/delete)**: Always delete — we don't use it in the fork.
   - For all other conflicts, **show the user your proposed resolution** using `AskUserQuestion`. Display the conflicting sections and your proposed fix, and ask the user to confirm or provide an alternative.
   - After resolution (auto or confirmed), apply the fix, **record the entry in your resolution log**, and run `git add {file}` to mark it resolved.
4. After all conflicts are resolved, finalize the merge with `git commit --no-edit`.

If a conflict is too complex to resolve automatically, show it to the user and ask for guidance.

## Step 7: Regenerate the lock file and verify compilation

If `Cargo.lock` was conflicted or if dependencies changed, run from the `quickwit/` directory:

```
cargo check --workspace --all-targets
```

This regenerates `Cargo.lock`, regenerates proto codegen via `build.rs`, and verifies compilation of lib **and** tests/benches/examples. Fix any compilation errors.

**Watch for silent damage from the merge.** Auto-merge can drop lines that touch our fork-only code without flagging a conflict — common patterns:

- **Dropped workspace dependencies** (e.g. `metrics`, `metrics-exporter-dogstatsd`, `quickwit-dst`) when upstream's adjacent edits won the textual merge. Compare against `main` if you see `dependency.X was not found in workspace.dependencies` or `unresolved crate X`.
- **Unused imports** left dangling after upstream removed the code that used them — common in `quickwit-proto/src/lib.rs`. Drop them.
- **Upstream API changes that don't conflict textually** — e.g. a new required field on a proto struct (`SearchResponse.resource_stats`), a trait moving methods (`rand::RngExt`'s `random_range`). Fork-only call sites still compile against the old shape and break at `cargo check`.

**Maintain a "post-merge fixes" log** alongside the conflict resolution log — same `(path, one-line rationale)` shape — for the PR body.

## Step 8: Regenerate 3rd-party licenses

**IMPORTANT**: This must run AFTER `cargo check` (Step 7), since the license tool needs the up-to-date `Cargo.lock`.

Always run this step, even if `Cargo.lock` was not conflicted — upstream dependency changes may introduce new licenses.

Run from the `quickwit/` directory:

```
make update-licenses
```

This runs `dd-rust-license-tool` and moves the generated `LICENSE-3rdparty.csv` to the repo root.

Check if the file actually changed with `git diff --stat LICENSE-3rdparty.csv`.

## Step 9: Commit license updates and post-merge fixes

Stage and commit the regenerated files plus any post-merge fixes from Step 7:

```
git add LICENSE-3rdparty.csv quickwit/Cargo.lock <other-fix-paths>
git commit -m "Post-merge fixes: regen lock + licenses, <one-line summary>"
```

(Only include files that actually changed. If `LICENSE-3rdparty.csv` was unchanged, omit it. If `cargo check` produced no fixes beyond regen, the commit message can be simpler.)

## Step 10: Push and open a PR

Push the branch:

```
git push -u origin {branch-name}
```

Build the PR body from the **resolution log** (Step 6) and the **post-merge fixes log** (Step 7). Use this template — group conflicts by strategy so a reviewer can scan quickly. Be specific in each one-liner (name the function/field/dep, not just the file). Omit empty sections.

```markdown
## Summary
Merges latest upstream OSS changes into the private DataDog fork.

## Conflict resolutions (N files)

**Take ours** (fork-specific code or files we own):
- `path/to/file` — short rationale referencing the specific thing kept.

**Take theirs:**
- `path/to/file` — short rationale.

**Merge both sides:**
- `path/to/file` — what came from each side.

**Take ours, will be regenerated:**
- `path/to/file` — regenerated by `<tool>` (cargo check / build.rs / make update-licenses).

## Post-merge fixes (separate commit)
Things `cargo check` surfaced that weren't visible as conflict markers:
- `path/to/file` — what broke and how it was fixed.

## Verification
- `cargo check --workspace --all-targets` passes locally.
- `LICENSE-3rdparty.csv` <changed | unchanged> after regen.
```

Create the PR with the body via heredoc to preserve formatting:

```
gh pr create --title "Merge oss/main ({date})" --body "$(cat <<'EOF'
<body from template above>
EOF
)"
```

If `gh` is not authenticated, ask the user to run `gh auth login` (via `! gh auth login`) and then create the PR. Do **not** silently fall back to a generic body — the per-conflict summary is the point of this step.

Report the PR URL to the user when complete.
